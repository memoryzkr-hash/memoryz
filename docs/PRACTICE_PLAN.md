# 연습 계획 — 프롬프트 8단계로 작은 앱 하나 끝까지 만들기

참고: [클로드 코드로 앱 만드는 프롬프트 8가지](https://every-ai-guides.vercel.app/posts/claude-code-app-prompts-8)

글에서 쓰는 8단계(범위 → 화면 → 데이터 → 구현 → 테스트 → 수정 → 출시 점검 → 문서)를
이 저장소에서 그대로 한 번 따라 해 보는 연습입니다. 게임처럼 큰 걸 만드는 게 아니라
**작은 앱 하나를 단계마다 멈추고 확인하면서** 끝까지 가 보는 게 목표입니다.

## 연습용 앱: 오늘셋 (`today.html`)

글의 예제와 같은 앱을 고릅니다. 같은 앱이라야 단계마다 내 결과를 글의 결과와 비교할 수 있습니다.

- 한 줄 설명: 오늘 꼭 할 일 **딱 3개**만 고르고, 끝내면 체크하는 모바일 우선 할 일 앱
- 스택: 이 저장소 그대로 — Vite + TypeScript, 테스트는 vitest, 저장은 `localStorage`
- 위치: `today.html` + `src/today/` + `tests/today/` (Royale·네온 라이더와 같은 방식의 별도 페이지)
- 배포: `vite.config.ts`의 `input`에 `today`를 추가하면 기존 GitHub Pages 배포에 `/memoryz/today.html`로 함께 올라갑니다.

> 다른 앱으로 바꾸고 싶으면 1단계 프롬프트의 앱 설명만 바꾸면 됩니다. 나머지 단계는 그대로 씁니다.
> 단, 첫 연습은 **화면 2~3개, 기능 3개 이하**로 작게 유지하세요.

## 진행 규칙

1. **한 단계 = 한 메시지.** 프롬프트를 붙여 넣고, 결과를 읽고, 완료 기준을 확인한 다음에만 다음 단계로 갑니다.
2. **산출물은 파일로 남깁니다.** 1~3단계와 7단계 결과는 `docs/today/`에 마크다운으로 저장해 달라고 합니다.
   다음 단계 프롬프트는 앞 단계 파일을 입력으로 씁니다 ("`docs/today/01-scope.md`를 기준으로…").
3. **모르면 묻게 합니다.** 1단계에서 Claude가 질문하면 바로 답하고, 추측으로 채우지 않게 합니다.
4. **단계마다 커밋합니다.** 나중에 `git log`만 봐도 8단계가 보이게, 커밋 메시지 앞에 `[today 0N]`을 붙입니다.
5. 단계 결과가 마음에 안 들면 다음으로 넘어가지 말고 **그 단계 안에서** 고칩니다.

## 8단계

### 01 범위 정하기 (Scope Planner)
- 입력: 앱 아이디어 한 줄 → 출력: `docs/today/01-scope.md`
- 프롬프트:
  ```
  "오늘셋"이라는 앱을 만들려고 해. 직장인이 아침에 오늘 꼭 할 일 3개만 고르고, 끝내면 체크하는 앱이야.
  코드는 아직 쓰지 마. 핵심 기능 3개와 이번에 '안 만드는 것'을 정해 줘.
  기능마다 사용자가 직접 눈으로 확인할 수 있는 완료 조건을 붙여 줘.
  애매한 건 추측하지 말고 나한테 먼저 질문해. 결과는 docs/today/01-scope.md로 저장해.
  ```
- 완료 기준: 기능 3개 이하, 각 기능에 "~하면 ~가 보인다" 형태의 완료 조건, 안 만드는 것 목록(로그인, 동기화 등)

### 02 화면 설계 (Screen Designer)
- 입력: `01-scope.md` → 출력: `docs/today/02-screens.md`
- 프롬프트:
  ```
  docs/today/01-scope.md의 기능을 화면 흐름으로 나눠 줘. 화면마다 보이는 요소, 버튼을 누르면 어디로 가는지,
  빈 상태(할 일 0개)와 오류 상태(저장 실패, 너무 긴 입력)도 적어 줘.
  가로 390px 모바일 화면을 기준으로 배치해. 코드는 아직 쓰지 마. 결과는 docs/today/02-screens.md로 저장해.
  ```
- 완료 기준: 모든 기능이 최소 한 화면에 연결됨, 빈/오류 상태가 화면별로 적혀 있음

### 03 데이터 설계 (Data Architect)
- 입력: `02-screens.md` → 출력: `docs/today/03-data.md`
- 프롬프트:
  ```
  docs/today/02-screens.md를 기준으로 저장할 데이터를 설계해 줘.
  필드 표(이름, 타입, 필수 여부, 제한), 만들기/읽기/수정/삭제 규칙, 검증 규칙(빈 값, 최대 길이, 3개 초과),
  localStorage 키 이름, 날짜가 바뀌었을 때 처리 방법을 적어 줘.
  올바른 예시 데이터와 잘못된 예시 데이터도 각각 3개씩 넣어 줘. 결과는 docs/today/03-data.md로 저장해.
  ```
- 완료 기준: 최대 길이를 **글자 수로 셀지(이모지 포함)** 정해져 있음 — 글의 예제가 여기서 버그가 났습니다.

### 04 구현 (App Builder)
- 입력: 01~03 문서 → 출력: `today.html`, `src/today/*`
- 프롬프트:
  ```
  docs/today/의 01~03 문서대로 오늘셋을 구현해 줘.
  이 저장소 방식대로 today.html + src/today/ 로 만들고, vite.config.ts의 input에 추가해.
  저장/검증 같은 순수 로직은 src/today/store.ts처럼 DOM과 분리해서 테스트할 수 있게 해.
  문서에 없는 기능은 추가하지 말고, 실행해 보지 못한 부분이 있으면 따로 표시해 줘.
  ```
- 완료 기준: `npm run dev` 후 http://localhost:5173/today.html 에서 3개 추가 → 체크 → 새로고침 후에도 유지

### 05 테스트 (Test Engineer)
- 입력: 구현 코드 → 출력: `tests/today/*.test.ts`, 실패 로그
- 프롬프트:
  ```
  src/today/의 로직에 대한 vitest 테스트를 tests/today/에 만들어 줘.
  정상 입력, 빈 입력, 공백만 있는 입력, 최대 길이(이모지·한글 포함), 4번째 추가 시도, 저장 후 다시 불러오기,
  날짜 변경을 꼭 넣어 줘. npm test를 실행하고 통과/실패 개수와 실패 로그를 그대로 보여 줘. 아직 고치지는 마.
  ```
- 완료 기준: 테스트가 실제로 실행됐고 결과 숫자가 있음. 실패가 0개여도 괜찮지만, 그럴 땐 "일부러 깨뜨려서 테스트가 잡는지" 한 번 확인
- (선택) 브라우저 테스트: Playwright로 390px 화면에서 클릭·입력 흐름 확인 — 글에서는 로직 테스트는 다 통과했는데 브라우저 테스트에서 `maxlength`와 이모지 문제가 나왔습니다.

### 06 버그 수정 (Bug Fixer)
- 입력: 5단계 실패 로그 → 출력: 수정 커밋, 재실행 결과
- 프롬프트:
  ```
  방금 실패한 테스트 로그를 보고 원인을 하나씩 찾아 줘. 원인마다 근거(로그 줄, 코드 위치)를 먼저 설명하고,
  필요한 최소한만 고쳐. 테스트를 지우거나 기대값을 바꿔서 통과시키지는 마.
  고친 뒤 npm test를 다시 돌려서 전/후 결과를 비교해 줘.
  ```
- 완료 기준: 전체 통과, 테스트 코드는 그대로이거나 늘어남, `npm run build`도 통과

### 07 출시 점검 (Release Checker)
- 입력: 최종 코드 → 출력: `docs/today/07-release.md`
- 프롬프트:
  ```
  오늘셋을 GitHub Pages(/memoryz/ 하위 경로)에 배포한다고 보고 점검해 줘.
  파일 경로(상대 경로인지), localStorage를 못 쓸 때(사생활 보호 모드), 오류 처리, 390px 화면, 
  빌드 결과물에 today.html이 들어가는지를 체크리스트로 만들고 하나씩 실제로 확인해 줘.
  결과는 docs/today/07-release.md로 저장해.
  ```
- 완료 기준: 체크리스트의 각 항목에 "확인함 / 문제 있음 / 확인 못 함"이 붙어 있음

### 08 문서화 (Documentation Writer)
- 입력: 1~7단계 기록 → 출력: README 섹션
- 프롬프트:
  ```
  지금까지의 docs/today/ 문서와 커밋 기록을 보고 README.md에 "오늘셋" 섹션을 추가해 줘.
  실행 방법, 파일 구조, 알려진 한계, 다음에 할 일(우선순위 순서)을 넣어 줘. 기존 섹션 형식에 맞춰.
  ```
- 완료 기준: README만 보고 다른 사람이 실행할 수 있음

## 일정 (예시)

| 회차 | 단계 | 예상 시간 | 끝났을 때 상태 |
| --- | --- | --- | --- |
| 1회차 | 01 → 03 | 40분 | 코드 없이 문서 3개 |
| 2회차 | 04 → 06 | 60분 | 동작하는 앱 + 통과하는 테스트 |
| 3회차 | 07 → 08 | 30분 | 배포 점검 + README |

## 끝나고 돌아볼 질문

- 어느 단계에서 Claude가 질문을 했고, 그 질문이 없었다면 어떤 잘못된 가정이 들어갔을까?
- 3단계에서 정한 규칙 중 4단계 구현에서 빠진 게 있었나? 5단계 테스트가 그걸 잡았나?
- 글의 결과(로직 9/9, 브라우저 11개 중 2개 실패 → 수정 후 11/11)와 내 결과는 어떻게 달랐나?
- 다음엔 어떤 단계를 합치거나 뺄 수 있을까? (예: 작은 앱이면 02와 03을 한 번에)
